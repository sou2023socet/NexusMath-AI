# 1. Project Identity

## 1.1 Project title

### NexusMath-AI

The name combines three ideas:

- **Nexus:** A central connection point joining different subjects, tools, algorithms and learning paths.
- **Math:** The primary computational and educational foundation of the platform.
- **AI:** The intelligent orchestration layer that interprets user requests, selects domain operations and constructs multi-step workflows.

### Full title

> **NexusMath-AI: A deterministic, explainable and interactive platform for Mathematics, Physics and Data Structures & Algorithms.**

### Short description

NexusMath-AI is a full-stack educational, scientific and algorithmic computing platform. It provides structured theory, formula-based calculators, symbolic and numerical computation, Physics simulations, DSA visualisations, step-by-step execution traces, learning paths and an agentic problem-solving workflow.

The platform separates:

1. **Understanding and orchestration**, which interprets a user’s request.
2. **Domain computation**, which performs trusted mathematical, scientific or algorithmic operations.
3. **Presentation**, which displays explanations, formulas, graphs, simulations and execution traces.

# 2. Abstract

NexusMath-AI is an on-premise, modular and explainable platform for learning and solving problems in Mathematics, Physics and Data Structures & Algorithms.

The system is designed to support Mathematics from beginner arithmetic through advanced subjects such as real analysis, linear algebra, multivariable calculus, numerical methods, optimisation and mathematical modelling. It also provides a selected Physics curriculum and an interactive DSA environment containing data structures, algorithms, complexity analysis and visual execution.

The platform uses a separate Angular frontend and Java Spring Boot backend. The frontend provides theory pages, calculators, structured forms, chat interfaces, graphs, simulations, algorithm animations, user workspaces and progress tracking. The backend provides authenticated REST APIs, deterministic computation services, validation, parser logic, theory management, calculation history and agentic workflow orchestration.

The central principle is that conversational or AI-based interpretation must not directly determine numerical results. A request is first transformed into a structured and validated task. The task is then executed by a registered Mathematics, Physics or DSA engine. The platform records the input, assumptions, formulas, intermediate values, execution steps, warnings and final result.

The system is therefore intended to be:

- Deterministic.
- Explainable.
- Auditable.
- Modular.
- Extensible.
- Educational.
- Secure.
- Suitable for local or controlled deployment.

# 3. Goals

## 3.1 Primary goal

The primary goal is to create a unified environment where users can learn, calculate, experiment, visualise and solve problems across Mathematics, Physics and DSA.

## 3.2 Version 1 goals

Your Version 1 scope is intentionally large:

- Cover 100% of the planned Mathematics roadmap at the topic level.
- Implement approximately 20–40% of Physics.
- Implement approximately 30–40% of DSA.
- Provide theory for every planned topic.
- Provide functional calculators and engines for appropriate topics.
- Provide visualisation for graphs, geometry, simulations and algorithms.
- Provide step-by-step traces.
- Provide user accounts and history.
- Provide structured and free-form workflows.
- Maintain separation between frontend and backend.
- Provide a foundation for future AI-enhanced learning.

“100% Mathematics” should be measured by a formal topic registry. A topic can be marked as:

- Theory complete.
- Formula complete.
- Calculator complete.
- Symbolic solver complete.
- Numerical solver complete.
- Visualisation complete.
- Exercise complete.
- Fully functional.

This is more accurate than requiring every Mathematics topic to be implemented as a calculator.

## 3.3 Engineering goals

- Use a modular architecture.
- Keep controllers thin.
- Keep domain logic inside domain services.
- Use strongly typed DTOs.
- Validate all external input.
- Preserve numerical precision.
- Prevent unsafe AI-generated computation.
- Maintain complete test coverage for core engines.
- Support independent deployment of frontend and backend.
- Provide versioned APIs.
- Maintain backward compatibility where possible.

## 3.4 Educational goals

- Explain concepts in simple and advanced language.
- Show prerequisites before advanced topics.
- Provide worked examples.
- Connect theory to practical applications.
- Show formulas in readable LaTeX.
- Provide exercises and solutions.
- Track learning progress.
- Support multiple learner levels.
- Visualise abstract concepts.
- Help users understand the method, not only the answer.

# 4. Vision

## 4.1 Long-term vision

The long-term vision of NexusMath-AI is to become an intelligent scientific learning environment in which a user can move seamlessly between:

```text
Learn → Ask → Calculate → Visualise → Practise → Save → Review
```

A user should be able to:

- Learn the definition of a derivative.
- View its prerequisites.
- See a graph demonstrating the slope.
- Solve a derivative problem.
- Compare symbolic and numerical results.
- Ask for a related Physics application.
- Use a DSA algorithm to process the generated data.
- Save the entire workflow for later review.

## 4.2 Vision principles

### Trust

Every answer should have a source of computation, formula or algorithm.

### Explainability

The platform should display how a result was obtained.

### Determinism

The same validated input and computation version should produce reproducible output.

### Modularity

Each domain should be independently expandable.

### Education first

The result should improve understanding, not merely provide a number.

### Human control

Agentic workflows should be inspectable, interruptible and reviewable.

### Safety

Invalid units, invalid domains, unsafe inputs and unauthorised actions must be rejected.

## 5.1 Current problems

Learners and developers often use separate tools for:

- Mathematics theory.
- Formula calculators.
- Graph plotting.
- Physics calculations.
- Algorithm visualisation.
- Coding practice.
- Numerical methods.
- Problem-solving explanations.
- Saved learning history.

These tools often suffer from:

- Fragmented user experience.
- Inconsistent explanations.
- No prerequisite structure.
- No reliable step trace.
- No common history.
- Unclear assumptions.
- Incorrect unit handling.
- Weak algorithm visualisation.
- Uncontrolled AI-generated answers.
- Lack of auditability.

## 5.2 NexusMath-AI solution

NexusMath-AI addresses these problems by providing a central platform with:

- One unified workspace.
- Domain-specific modes.
- A searchable theory system.
- Deterministic computation engines.
- Unit-aware Physics services.
- Visual DSA execution.
- Step-by-step traces.
- User history.
- Progress tracking.
- Controlled agentic orchestration.
- Clear separation between interpretation and computation.

## 8.3 Domain Chat

Domain Chat should require a selected domain:

- Mathematics.
- Physics.
- DSA.

The selection prevents semantic confusion. For example:

- “Momentum” in Physics differs from a momentum-like concept in an algorithmic context.
- “Root” may mean a polynomial root or a tree root.
- “Power” may mean exponentiation, electrical power or computational power.

Domain Chat should support:

- Topic-aware conversations.
- Formula explanations.
- Follow-up questions.
- Related examples.
- Clarification requests.
- Links to the Function Module.
- Links to Theory Encyclopedia.
- Conversation history.

## 8.4 Autonomous Agent

The Autonomous Agent accepts free-form requests and constructs a task workflow.

Example:

```text
Calculate the maximum height and range of a projectile,
plot its trajectory and explain the assumptions.
```

Possible workflow:

```text
1. Detect Physics domain.
2. Extract initial velocity and angle.
3. Request missing gravity if necessary.
4. Validate units.
5. Calculate time of flight.
6. Calculate maximum height.
7. Calculate range.
8. Generate trajectory samples.
9. Render graph.
10. Save execution history.
```

# 9. Application Modes

## 9.1 Application Mode

Application Mode is the deterministic mode.

Characteristics:

- Structured forms.
- Explicit parameters.
- No ambiguous natural-language parsing.
- Strict input validation.
- Synchronous or controlled asynchronous execution.
- Typed REST DTOs.
- Step-by-step result.
- Immutable history.

Example:

```text
Operation: Solve Quadratic Equation

a = 1
b = -5
c = 6
```

The system directly invokes the quadratic solver.

## 9.2 Agentic Mode

Agentic Mode is the workflow mode.

Characteristics:

- Free-form request.
- Domain detection.
- Parameter extraction.
- Clarification.
- Task decomposition.
- DAG construction.
- Registered operation selection.
- Dependency execution.
- SSE progress.
- Intermediate results.
- Final explanation.

The AI should not invent a new formula implementation at runtime. It should select and connect approved operations.

## 10.4 Layered backend structure

```text
Controller
   ↓
Application Service
   ↓
Domain Service
   ↓
Algorithm / Calculation Engine
   ↓
Trace Builder
   ↓
Persistence Adapter
```

### Controller

Responsible for:

- Authentication.
- DTO validation.
- Calling the application service.
- Returning an HTTP response.
- Mapping errors.

### Application service

Responsible for:

- Use-case orchestration.
- Calling domain services.
- Creating history records.
- Preparing response DTOs.

### Domain service

Responsible for:

- Mathematical, Physics or DSA logic.
- Domain validation.
- Assumption handling.
- Trace generation.

### Engine

Responsible for:

- The actual algorithm or calculation.
- No HTTP logic.
- No database logic.
- No UI logic.

### Repository

Responsible for:

- Persistence.
- Querying.
- Indexes.
- Data access.

# 14. Validation and Error Handling

## 14.1 Validation layers

Validation must occur at:

1. Frontend form level.
2. API DTO level.
3. Application-service level.
4. Domain-service level.
5. Repository level where applicable.

## 14.2 Mathematics validation

Examples:

- Denominator cannot be zero.
- Logarithm argument must satisfy its domain.
- Even root radicand cannot be negative in real mode.
- Matrix dimensions must be compatible.
- Variable values must be bound.
- Probability must be between zero and one.
- Iterative algorithms must have valid convergence parameters.

## 14.3 Physics validation

Examples:

- Units must be convertible.
- Dimensions must be compatible.
- Kelvin temperature cannot be negative.
- Mass cannot be negative.
- Time intervals must be valid.
- Resistance cannot be zero when calculating current from voltage.
- Physical assumptions must be displayed.

## 14.4 DSA validation

Examples:

- Binary search requires sorted input.
- Graph vertices must be unique.
- Edge weights must be valid for the selected algorithm.
- Dijkstra must reject negative edge weights.
- Tree operations must preserve invariants.
- Array size must be within configured limits.

# 23. Risks and Mitigation

| Risk | Mitigation |
|---|---|
| Scope becomes too large | Use topic registry and implementation statuses |
| AI generates incorrect algorithms | Restrict AI to registered engines |
| Floating-point errors | Use exact types or documented tolerances |
| Physics produces invalid results | Add unit and dimension validation |
| Frontend and backend drift | Use versioned DTOs and contract tests |
| Large calculations exhaust resources | Add execution limits and cancellation |
| Database history grows indefinitely | Pagination, retention and archival |
| Agent creates invalid DAG | Schema validation and cycle detection |
| Security vulnerabilities | CI security scanning and reviews |
| Inconsistent theory content | Versioned editorial workflow |
| Poor user experience | UX testing and domain-specific layouts |

# Final Project Statement

NexusMath-AI should be developed as:

> **A secure, explainable and deterministic learning-and-computation platform that connects complete Mathematics coverage with selected Physics and DSA functionality through a modular Java backend, independent Angular frontend, interactive visualisations and controlled AI orchestration.**

The most important implementation rule is:

> **The AI may interpret, plan, explain and connect operations, but trusted domain engines must validate and perform the actual computation.**

This architecture preserves your ambition to cover complete Mathematics while keeping the platform reliable, testable, extensible and suitable for future Physics, DSA, AI and institutional features.
